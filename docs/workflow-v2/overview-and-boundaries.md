# Workflow V2 概览与边界

## 定位

Workflow V2 是一套多智能体编排系统。它关注的不是“多跑几个 agent”，而是如何把复杂任务拆成可执行、可审查、可恢复的图。

总方向已经明确：

- Manager / Orchestrator 负责理解目标与编排
- Worker / Executor 负责高频执行
- Reviewer 负责独立验收
- 人类始终可在关键节点介入

## 目标

Workflow V2 要解决的核心问题：

- 让复杂任务可以被拆成多个节点稳定执行
- 让高成本专家模型只用在真正需要全局判断的地方
- 让低成本快速模型承担阅读、检索、实现、测试等高频工作
- 让审查、打回、重试和人工介入成为系统内能力
- 让长链路执行在上下文、成本和恢复性上保持可控

## 核心原则

- **自由编排优先**：Manager 直接产出图定义，模板只是辅助
- **角色分层优先**：编排、执行、验收不混在一个 agent 身上
- **默认低成本执行**：能用 fast model 做完的工作，不默认占用 expert model
- **边保持极简**：边只表达依赖，不塞进过多语义
- **数据控制分离**：Worker 负责数据，Leader 负责导航与裁决
- **验证分层**：机械校验前置，语义质量后置
- **执行期可恢复**：暂停、恢复、缓存复用是一等能力

## 角色分层概览

Workflow V2 默认采用三层角色：

| 角色 | 默认模型 | 主要职责 |
|------|----------|----------|
| `orchestrator` | expert | Clarify、拆解、编排、升级决策、阶段总结 |
| `executor` | fast | 阅读局部上下文、搜索、实现、测试、产出初稿 |
| `reviewer` | expert | 独立审查、对抗式找错、放行或打回 |

推荐链路：

`Orchestrator -> Executor Swarm -> Reviewer -> Orchestrator`

## 边界

当前设计边界：

- MVP 只要求支持 `llm` 和 `script` 两种执行模型
- 模板是快捷方式，不是类型约束
- 边只表达依赖，不承担审查、打回、条件分支等复杂语义
- 图在进入执行阶段后默认冻结，需要改动时走显式修订

## 非目标

MVP 不追求：

- 复杂边语义系统
- 一次性覆盖所有执行模型
- 在总纲里容纳全部 schema、状态机、事件协议与落盘细节

这些内容应拆到独立模块文档中。
